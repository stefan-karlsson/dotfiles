# Keep a managed channel authoritative for its packages

A repository is enrolled the way its vendor's own package enrolls it, and stays authoritative for the packages it owns. Two things break that on a company laptop, and both are settled in the repository data rather than by hand.

A vendor whose package rewrites its own apt source at every install and upgrade wins over anything this source state writes to the same file. Microsoft Edge does exactly that: its `postinst` recreates `/etc/apt/sources.list.d/microsoft-edge.sources` with `packages.microsoft.com/repos/edge-stable` and its own keyring, so a channel declared any other way survives only until the next Edge release and is then read as a foreign repository. The declared channel therefore matches what that script writes, including the keyring path — the same Microsoft release-signing key the rest of this setup pins, in a second file — and a repeated field in the stanza the script generates is read as the single field apt reads it as.

A general-purpose vendor channel added for one application may also carry packages another channel owns. `packages.microsoft.com/ubuntu/26.04/prod`, enrolled for the Intune Portal, also carries `kubectl`, with a version string that outranks the Kubernetes channel's, so apt moved the client off the pinned channel without being asked. A repository may therefore pin its own packages to itself through an apt preferences file, at a priority above 1000 so that a laptop that has already drifted is brought back rather than left where it landed. The pin names the package rather than demoting the other channel, so it holds against any future channel that carries the same package, and the preflight treats a drifted version as drift this apply corrects rather than as an installation the setup does not own.
